# 05 · 借书 / 还书时序图

> 这张图回答一个问题：**点一下「借书」，浏览器到数据库之间到底发生了什么？为什么并发时会超借？**

---

## 一、借书时序图（正常路径）

```mermaid
sequenceDiagram
    autonumber
    participant U as 用户浏览器
    participant R as React 前端
    participant F as FastAPI 后端
    participant D as MySQL 8
    U->>R: 点击「借书」按钮
    R->>F: POST /api/borrows/borrow<br/>Authorization: Bearer xxx<br/>请求体 { bookId, readerId }
    F->>F: 校验 JWT 签名与 exp，再校验角色权限（失败直接 401，不进事务）
    F->>D: BEGIN · 开启事务
    F->>D: SELECT * FROM books WHERE id = ? FOR UPDATE
    Note over D: 🔒 行锁生效，并发的第二个请求会在这里排队等待
    D-->>F: 图书行 · stock = 1
    F->>D: SELECT COUNT(*) FROM borrow_records WHERE book_id = ? AND return_date IS NULL
    D-->>F: 未归还借阅数 = 0
    F->>D: SELECT COUNT(*) FROM reservations WHERE book_id = ? AND status = 'available'
    D-->>F: 已到书待取占位数 = 0
    F->>F: available = stock − 未归还数 − 占位数 = 1
    alt 库存不足（available 等于 0）
        F->>D: ROLLBACK · 回滚事务
        F-->>R: 400 Bad Request · 库存不足
        R-->>U: Toast 提示「这本书已被借完」
    else 库存充足
        F->>D: INSERT INTO borrow_records (book_id, user_id, borrow_date, due_date)
        F->>D: UPDATE books SET available = 1 WHERE id = ?
        F->>D: COMMIT · 提交事务
        F-->>R: 201 Created · 借阅成功
        R->>R: 重新拉取列表接口（绝不手工改本地库存）
        R-->>U: 列表刷新 + Toast 成功提示
    end
```

**三个必须记住的点：** ① `SELECT ... FOR UPDATE` —— 没有行锁，5 个并发请求会同时读到 `available = 1`；② `available` 必须重算而不是 `- 1` —— 加减法散落多处必然错位；③ 前端刷新列表而不是本地减 1 —— 库存和状态只能由后端算。

## 二、并发场景 · 两个人同时借同一本书（stock = 1 · available = 1）

```mermaid
sequenceDiagram
    autonumber
    participant A as 请求 A（读者张三）
    participant B as 请求 B（读者李四）
    participant D as MySQL 8
    Note over D: 初始状态：stock = 1 · available = 1
    A->>D: BEGIN
    A->>D: SELECT * FROM books WHERE id = 1 FOR UPDATE
    D-->>A: 拿到图书行 · A 持有行锁
    Note over A,D: 🔒 请求 A 持锁成功
    B->>D: BEGIN
    B->>D: SELECT * FROM books WHERE id = 1 FOR UPDATE
    Note over B,D: ⏳ 请求 B 在这里阻塞等待 —— 不报错，就是等<br/>直到 A 提交或回滚，最长等 innodb_lock_wait_timeout（默认 50 秒）
    Note over B: 前端表现：请求一直 pending，按钮转圈
    A->>D: COUNT 未归还借阅数 = 0
    A->>D: UPDATE books SET available = 0 WHERE id = 1
    A->>D: INSERT INTO borrow_records (book_id = 1, user_id = 张三)
    A->>D: COMMIT
    D-->>A: ✅ 201 借阅成功
    Note over D: 🔓 行锁随事务提交自动释放
    D-->>B: 锁释放 · B 拿到图书行
    Note over B: READ COMMITTED 读到 available = 0<br/>若用默认 REPEATABLE READ 会读旧快照 = 1 → 判定有库存 → 超借 🐛
    B->>D: COUNT 未归还借阅数 = 1
    B->>D: ROLLBACK
    D-->>B: ❌ 400 库存不足
    Note over A,B: 最终结果：1 个 201 + 1 个 400，库存没有超卖
```

| 修复措施 | 5 并发借 1 本书的结果 |
|---|---|
| 什么都不做 | 5 个 `201` —— 一本书借出去 5 次 |
| **只加 `FOR UPDATE`** | **4 个 `201`** —— 锁了个寂寞 🐛 |
| 加锁 + `READ COMMITTED` | 1 个 `201` + 4 个 `400` ✅ |

## 三、还书时序图（含预约队列晋升）

```mermaid
sequenceDiagram
    autonumber
    participant U as 用户浏览器
    participant R as React 前端
    participant F as FastAPI 后端
    participant D as MySQL 8
    U->>R: 点击「归还」
    R->>F: POST /api/borrows/return · 请求体 { recordId }
    F->>D: BEGIN · 开启事务
    F->>D: SELECT * FROM borrow_records WHERE id = ? FOR UPDATE
    Note over D: 🔒 ① 先锁「借阅记录」行，防止同一条记录被重复归还
    D-->>F: 记录行 · return_date IS NULL，校验通过
    F->>D: SELECT * FROM books WHERE id = ? FOR UPDATE
    Note over D: 🔒 ② 再锁「图书」行，加锁顺序必须全局统一，否则死锁
    D-->>F: 图书行 · stock = 1
    F->>F: 判断是否逾期（今天是否晚于 due_date）
    F->>D: UPDATE borrow_records SET return_date = CURDATE() WHERE id = ?
    F->>F: 重算 available = stock − 未归还数 − 已到书待取占位数
    F->>D: SELECT * FROM reservations WHERE book_id = ? AND status = 'waiting' ORDER BY queue_position LIMIT 1 FOR UPDATE
    alt 队列里有人预约
        D-->>F: 队首预约记录
        F->>D: UPDATE reservations SET status = 'available', expire_at = NOW() + 3 天
        Note over F: 占位数 +1，available 不增加 —— 这本书留给预约者
    else 无人预约
        D-->>F: 空结果集
        Note over F: 库存真正释放，available 增加 1
    end
    F->>D: UPDATE books SET available = ? WHERE id = ?
    F->>D: COMMIT · 提交事务
    F-->>R: 200 OK · 归还成功
    R-->>U: 列表刷新；有预约则提示「已通知下一位预约者」
    Note over F: 预约占位的两种出口：取书 → status = picked（真正借出）；超期未取 → status = expired（重算 available）
```

**加锁顺序：** 借书是「图书行 → 借阅记录」，还书是「借阅记录 → 图书行」。**全局顺序必须统一**，一个事务先锁书记录、另一个先锁记录再锁书，就会交叉等待形成 💀 **死锁**（MySQL 报 `Deadlock found`，随机杀掉其中一个事务）。

## 四、为什么必须用 READ COMMITTED

| 对比维度 | REPEATABLE READ（MySQL 默认） | READ COMMITTED（本项目采用） |
|---|---|---|
| MVCC 快照建立时机 | 事务中**第一次读**时建立，之后不再变 | **每条语句**开始时都重建 |
| 行锁内读到的数据 | 旧快照里的 `available = 1` | 最新已提交的 `available = 0` |
| 5 并发借 1 本书 | 4 个 `201`（超借 🐛） | 1 个 `201` + 4 个 `400` ✅ |
| `SELECT ... FOR UPDATE` | 锁生效了，但**读到的是过期数据** | 锁 + 最新数据，判断才正确 |
| 同一事务内两次读 | 结果始终一致（可重复读） | 可能不一致 |
| 代价 | —— | 失去可重复读能力，业务上必须能接受 |

**只加锁不改隔离级别是无效的，两件事必须同时做：**

```python
@event.listens_for(engine, "connect")
def _use_read_committed(conn, _):
    conn.cursor().execute("SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED")
```

关键查询还必须带 `with_for_update()`：`select(Book).where(Book.id == bid).with_for_update()`。

**三条铁律：** ① 库存和状态只能由后端算；② `available` 只能重算，不能手工 ±1；③ 行锁和隔离级别必须同时改，少任何一个并发借书照样超借。
